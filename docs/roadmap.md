# D.Lab 개발 로드맵 — 단계별 작업 분류

> **언제 읽나** — "다음에 뭘 구현하지?", "이거 지금 착수해도 되나?"를 판단할 때.
> **함께 보는 문서** — 엔드포인트 상세는 `docs/api-spec.md`, 도메인별 블로커는 `docs/domain-map.md`,
> 키오스크 계약은 `docs/dsa-compat.md`, 테이블 설계 근거는 `docs/schema-guide.md`.

## 편성 원칙

1. **블로커 없는 것부터.** §4 블로커에 걸린 도메인은 임의 가정으로 진행하지 않는다 (CLAUDE.md §6-3).
2. **외부 연동은 도메인 로직 안정 후.** Zyxel·더프리미엄·PG·채팅 SDK는 해당 도메인이 굳은 뒤 붙인다 (CLAUDE.md §6-2).
3. **화면 선개발 금지.** API·스키마 확정 전에 화면부터 만들지 않는다 (CLAUDE.md §6-1).

### 범례

**진행 상태** — ✅ 착수 가능 · 🟡 부분 착수 · ❌ 블로커 대기

**클라이언트 태그**

| 태그 | 의미 | 경로 |
|---|---|---|
| `공용` | **서비스·엔티티·리포지토리.** 여러 클라이언트가 함께 쓰는 비즈니스 로직 | `domain/**` |
| `앱` | 학생·학부모 앱이 호출하는 컨트롤러 | `api/app/**` |
| `웹` | 관리자 웹이 호출하는 컨트롤러 | `api/admin/**` |
| `키오스크` | DSA 호환 구획 (prefix·응답형식 예외) | `api/kiosk/**` → `/auth/**`, `/kiosk/**` |
| `서버` | 스케줄러·배치. 호출하는 클라이언트 없음 | — |
| `인프라` | 공통 계층·마이그레이션·설정 | `common/**`, `db/migration/**` |

> **⚠️ 태그를 "작업량"으로 읽지 말 것.**
> `앱`·`웹` 태그가 붙은 건 **얇은 컨트롤러 + DTO 층**이고, 실제 로직은 대부분 `공용`에 있다.
> 예: 승인 타임아웃·에스컬레이션·원자적 상태 전이는 학부모가 앱에서 누르든 선생님이 웹에서 누르든 **같은 `domain/approval` 코드**다.
> 그래서 특정 클라이언트를 담당에서 제외해도 실제로 빠지는 분량은 크지 않다 (Phase 4 제외).

## Phase 0 — 기반 ✅

모든 것의 선행. 블로커 없음. **전부 `인프라`라 클라이언트 구분이 없다.**

> **진행 현황 (2026-08-04)** — 공통 계층·Flyway는 `feature/phase0-approval-notification-attendance`,
> 인증(JWT + Redis Refresh/블랙리스트)은 PR #3에 구현됨. `YearlySnapshotService`는 아래 정정대로
> **Phase 2에서 구현 완료**. 남은 것은 **DSA 호환 구획의 `/kiosk/**` 부분** — 응답 껍데기·code 매핑·
> 전용 예외 핸들러와 `/auth/**`는 이미 있고, 엔드포인트 25개가 아직 없다.

**공통 계층** `인프라` — ✅ 구현됨
- `ApiResponse<T>` · `ErrorCode` · `GlobalExceptionHandler`
- JWT 인증 + **RBAC 5단계** (`SUPER_ADMIN` / `BRANCH_ADMIN` / `TEACHER`(담당선생님·사감) / `STAFF`(행정선생님) / `READONLY`)
- 지점 필터 공통 처리 (전 지점 조회는 상위 관리자만)
- 요청/응답 로깅

**DSA 호환 예외 구획** `인프라` — 반드시 Phase 1 전에
- `/auth/**`·`/kiosk/**` 전용 응답 객체 (`{code, message, data, …}`)
- 전용 예외 핸들러 (`ApiResponse` 래퍼·`GlobalExceptionHandler` **적용 제외**)
- `BusinessException` → DSA `code` 매핑 테이블

**Flyway — ★ 번호 분담 확정 (2026-08-03)** `인프라`

## Phase 1 — 키오스크 DSA 호환 25개 ✅ ★

**전부 `키오스크` + `공용`. 앱·웹 어느 쪽에도 의존하지 않아 혼자 완결된다.**
블로커 없음. 크리티컬 패스 — 학생이 매일 태깅하는 물건이라 컷오버 시점에 반드시 동작해야 한다.

| 그룹 | 개수 | 태그 | 상태 | 비고 |
|---|---|---|---|---|
| 인증 (`/auth/token` `/refreshToken`) | 2 | `키오스크` | ✅ | MD5(`yyyyMMdd`+secret), Redis 9일/99일, **자정 경계 처리** |
| 학생·지점·학부모 | 4 | `키오스크`+`공용` | ✅ | 원생MST/RLS 확보. `p_gb`는 F/M만 (기타 보호자 매핑 주의) |
| **출결** (`setAttendStd` `setReAttendProc`) | 2 | `키오스크`+`공용` | ✅ | 7종 상태 + 분기코드 6개 + `113` 2-phase 왕복 |
| 통계·상세 | 6 | `키오스크`+`공용` | ✅ | `attendance_daily`에서 집계 |
| 급식·상벌점·수납 조회 | 4 | `키오스크`+`공용` | ✅ | 레거시 확보. `getReceiptInfo`는 `TB_RECEIVE_MST`와 필드 일치 |
| 좌석 | 4 | `키오스크`+`공용` | ✅ | `state` 확정 — `S`착석 / `D`외출 / `B`빈좌석 |
| 사유 조회 | 1 | `키오스크`+`공용` | 🟡 | `reg_gn` 값 목록 미상 (키오스크 백엔드도 소비처 없음) |

### 이 Phase는 영구 계약이다

키오스크 백엔드(`doc/kiosk/deasung-kiosk-backend`) 확인 결과, DSA 주소가 **설정 한 줄**(`dsa.api.base-url`)이고
인증정보는 `stores` 테이블 3컬럼이다 → **코드 수정 없이 전환된다.**

그래서 **키오스크는 손대지 않기로 확정**했고, 이 25개는 과도기가 아니라 **영구히 유지할 인터페이스**다.
키오스크 백엔드가 자체 DB에 이중 보관·동기화하는 것도 그쪽 사정이므로 관여하지 않는다.

**지점 코드는 승계한다** — 9개, `acad_cd`가 연속이 아니다(분당 31 · 일산 32 · 동탄 33 · 김포 34 · 부천 42 · 이매 43 · 광명 44 · 목동 45 · 송파 46). 그쪽 DB에 박혀 있어 바꾸면 깨진다.

**검증 기준**: 키오스크 백엔드의 실제 파싱 코드(`DsaAreaService`·`DsaAttendanceService` 등)가 곧 스펙이다.

### ⚠️ 모니터링을 같이 붙여야 한다

키오스크 백엔드는 DSA 장애 대비 **관대한 폴백**을 갖고 있다 — `getMealApplyYN` 실패 시 **전부 허용**, `att_gn` 없으면 로컬 판별.
우리가 DSA 자리에 들어가면 **이 폴백이 우리 장애를 조용히 가린다**(서버가 죽어도 급식이 다 통과).
**키오스크 무수정 결정으로 폴백은 제거 불가**하므로, `/kiosk/**` 에러율·응답시간을 **우리 쪽에서 독립 감시**해야 한다.

**`setAttendStd`가 이 프로젝트 출결의 심장이다.**
- 상태 7종: `S`등원 `T`하원 `A`지각 `D`외출 `N`사유외출 `C`조퇴 `R`복귀
- 분기코드가 **최상위(`121`·`130`)와 `data` 내부(`122`·`113`·`126`·`128`·`129`)로 갈려서** 온다
- `113`은 **stateless 2-phase** — 서버가 왕복 사이 상태를 들고 있으면 안 된다
- **응답을 "정리"하면 키오스크가 깨진다** (`data` 이중배열, `"N시간 M분"` 문자열, `meal_gb` 비대칭 등)

## Phase 2 — 회원·기초 마스터 ✅

**전부 `웹` + `공용`. 앱 무관.** 모든 도메인의 뿌리. **Phase 1과 병렬 가능.**

> **진행 현황 (2026-08-04)** — `feature/phase2-class-assignment`(PR #3)에 구현됨. 테스트 166건 통과.
> **남은 것은 교시 편집(다른 담당자 몫) 하나뿐이다.**

| 작업 | 태그 | 상태 |
|---|---|---|
| 학생 검색(12개 조건) · 신규 접수 · **학번 채번** `year + %04d`, `UNIQUE(year, student_no)` | `웹`+`공용` | ✅ 구현됨 |
| 반 배정 · **반별 담임(담당선생님) 지정** | `웹`+`공용` | ✅ 구현됨 |
| 직원·강사 계정, 권한 관리, 지점별 접근 제어 | `웹`+`공용` | ✅ 구현됨 |
| **교시·시간 편집 (지점 공통)** — API만. **별도 화면은 신설 안 함**(0803 폐기, 편집은 학습계획 화면 안에서 Phase 3) | `웹`+`공용` | ⬜ 담당자 작업 예정 |
| 학과 · 사물함 · 장학 | `웹`+`공용` | ✅ 구현됨 |
| 전형 · 과정 마스터 | `웹`+`공용` | ✅ 구현됨 |
| 학생 정보 수정 · **엑셀 일괄 업로드**(미리보기·오류행·유연매핑) | `웹`+`공용` | ✅ 구현됨 |
| 배정관리 — 사물함 · 독서실(좌석) · **기숙사** | `웹`+`공용` | ✅ 구현됨 |
| **전년도 복사** 실동작 | `웹`+`공용` | ✅ 구현됨 |

> **★ 전년도 복사는 단순 `INSERT SELECT`가 아니다.** 마스터끼리 FK로 물려 있어 그대로 복사하면
> **새 연도 행이 옛 연도 행을 가리킨다** — 옛 것을 지우거나 고칠 때 새 연도가 같이 망가진다.
> 갈아끼워야 하는 참조가 **둘**이다: `penalty_rule → penalty_item`, `class_master → course_type`.
> 항목·과정을 먼저 복사하면서 ID 매핑을 들고 다니며 참조를 새 연도 것으로 바꾼다.
> 함께 정한 것: **퇴사 담임은 비운다**(남기면 그 반 승인 요청이 아무에게도 안 간다) ·
> **복사된 규칙은 꺼진 채로**(I-5 미확정) · **대상 연도에 데이터가 있으면 409 거부**(두 벌 방지) ·
> **`SUPER_ADMIN`만 실행**. 복사 대상은 **8종**(학과·과정·전형·교시·반·승인정책·상벌점 항목/규칙).
> 교시만 네이티브 `INSERT SELECT`인데, 엔티티가 아직 없고 참조하는 연도별 마스터도 없어서
> 갈아끼울 FK가 없기 때문이다 — 교시 엔티티가 생기면 나머지와 같은 형태로 옮긴다.

> **반에 담임을 지정하면 학생 배정 시 방화벽 승인자가 자동 결정된다** (Phase 5 선행조건).
> 학생별로 승인자를 따로 지정하는 화면은 만들지 않는다 (CLAUDE.md §3).

## Phase 3 — 출결·상벌점·좌석 표면 🟡

Phase 1이 만든 데이터를 관리자 웹·앱에 노출하는 층.

| 작업 | 태그 |
|---|---|
| 출결 현황 조회(담당 반 필터) · 개별 수정 | `웹` |
| 상벌점 항목 마스터 · 수기 일괄 부여 | `웹`+`공용` |
| 좌석배치도 · 자리이탈 이력 | `웹` |
| 출결 조회 · 집계 | `앱` |
| **출결 QR** — ⚠️ **동적 토큰으로 미확정**(아래) | `앱` |
| 자리이탈 현황 조회 | `앱` |
| 결석 확정 배치 (`attendance_daily` 상태 확정) | `서버` |

> **출결 로직에 QR/카드 분기를 만들지 말 것** — 이건 유효하다.
>
> ⚠️ **다만 QR 내용이 정적 `rfid_no`인지는 확정이 아니다.** 0803 시트는 앱 화면을 `A-4 출결 조회·**동적** QR 태깅`으로, D-2에 *"앱 동적 QR 토큰 검증 방식 추가 협의 필요"*로 적었다. 실행가이드 지침: **"확정 전까지 QR 발급 인터페이스만 구현하고 검증 로직은 서버 목업으로 대체"**.

## Phase 4 — 앱 온보딩·인증 🟡

**거의 전부 `앱`.** 특정 담당에서 앱을 제외하면 **통째로 빠지는 유일한 Phase**다.
Phase 2의 `user` 도메인이 선행.

온보딩 4단계: **회원가입 → OT(대면) → 학부모 인증(알림톡) → 정기일정 등록**

| 작업 | 태그 |
|---|---|
| 휴대폰 인증 | `앱`+`공용` |
| **학생 가입** — 승인제. `PENDING` → 승인 → `ACTIVE`. **중간 상태 없음**, 승인 전 앱 접근 전면 차단 | `앱`+`공용` |
| **학부모 가입** — 학생 고유ID만 맞으면 즉시 `ACTIVE`. **관계 검증 안 함** | `앱`+`공용` |
| 로그인/토큰 (refresh·블랙리스트 Redis) | `앱`+`공용` |
| 마이페이지 — 학생 본인 고유ID 노출(학부모 연결용 유일 수단) | `앱` |
| **자녀 전환** — 계정 1개 + 자녀 N (자녀 수만큼 계정 분리 아님) | `앱`+`공용` |
| 앱 홈 — 프로필 · 3지표 · 퀵메뉴 8개 · 배너 알림 | `앱` |
| **학생 가입 승인** | `웹` |

> 학부모-자녀 관계를 검증하지 않는 건 클라이언트가 인지·감수한 리스크다. **추가 검증 로직을 임의로 만들지 말 것.**

⚠️ **내신 입력 양식 미정** — 학생 가입 흐름이 여기서 막힌다. 모의고사는 더프리미엄 자동조회라 무관.
⚠️ **순공시간 산출 정의(I-6)** — 홈 3지표에 필요.

**Phase 0 → 1 → 2 → 3이 블로커 없이 갈 수 있는 구간이다.**
그동안 운영팀·외부 업체 회신을 받아 Phase 5 이후를 푸는 것이 현실적이다.

### 앱을 담당에서 제외할 경우

| Phase | 영향 |
|---|---|
| 0 · 1 · 2 · 9 | **영향 없음** — 앱 대응 작업이 아예 없다 |
| 3 · 8 | 앱 컨트롤러 몇 개만 제외, 나머지 그대로 |
| 5 · 6 · 7 | **핵심 로직이 `공용`이라 대부분 그대로** — 앱 컨트롤러만 제외 |
| **4** | **통째로 빠진다** (`웹`인 "학생 가입 승인"만 남음) |

→ 앱 제외해도 **Phase 0 → 1 → 2 → 3 순서는 동일하고, 실질적으로 빠지는 건 Phase 4 하나뿐**이다.

### 병렬로 미리 돌려야 할 것 (개발 외 트랙)

- **★ Firebase/APNs(E-7)·스토어 계정 위임(S-5)** — **앱 스토어 심사는 12월 단 한 번**. Phase 0 필수이고 밀리면 앱 전체가 빌드 불가
- **카카오 알림톡 사전심사(E-5)** — 심사 리드타임이 길다. Phase 8을 기다리지 말고 지금 신청. **SMS 폴백이 폐기돼 대체 수단이 없다**
- **결제 법적요건** — 전자금융거래법·PG 등록·보증보험 검토
- **대성전산 스키마 4종** — 출결·좌석/구역·지점·사유신청. 안 와도 역산 설계로 진행하되, **컷오버 데이터 이관에는 반드시 필요**
- **운영팀 확정 항목** — I-1, I-6, I-12, I-17이 가장 많은 도메인을 막고 있다

## 만들지 말 것 — DSA 미사용 기능 (2026-08-04 클라이언트 회신)

클라이언트가 DSA 50개 기능에 사용 여부를 체크해 회신했다. **사용 19 / 미사용 31.**
추가 기재란은 전부 공란이라 별도 요청은 없다. (원본 정리: `doc/상세기능.md`)

**⚠️ "미사용" = "현재 DSA에 그 흐름이 없다"이지 "불필요"가 아니다.**
앱 신규 기능은 그대로 개발 대상이다. 이 목록의 용도는 **DSA 화면을 참고자료로 삼을 때 헛다리를 짚지 않는 것**이다.

### 통째로 빠지는 계열

| 계열 | 건수 | 내용 |
|---|---|---|
| **NEW 접수 > 접수관리** | 6 | 접수창 설정 · 지원기준 · 선택과목 설정 · 장학성적 설정 · 개인정보 문구 · 표준점수 |

### 개별 미사용

`교무업무 > 반배정` · `교무업무 > 모의고사` · `교무업무 > 선생님` · `선생님 교재 관리` · `출결/자습/독서실 > 출결현황` · `독서실 신청`

### ⭐ 클라이언트가 직접 추가한 항목

```
독서실 > 독서실 좌석배치표    ■ 사용   (원본 양식에 없던 항목)
```

**DSA에 좌석배치표(좌석맵)가 이미 존재한다.** V2에서 만든 `study_area` · `seat_master`(좌표) · `seat_assignment`의 **참조 화면이 있다는 뜻**이라 실사 가치가 있다.
반면 **독서실 "신청" flow는 없으므로**(미사용) 앱 신청 화면은 순수 신규다.

### 해석 주의 3가지

| # | 회신 | 실제 의미 |
|---|---|---|
| 1 | **합격생등록 미사용** | 요구사항 F-4.1-4(신규 접수 등록 + 학번 채번)는 유효하다. DSA의 그 메뉴를 안 쓸 뿐. **현재 학생 등록을 어디서 하는지 확인 필요** |
| 2 | **반배정 미사용** | `시간표·이동수업 > 고정반 관리`를 쓴다. F-4.1-5는 유효하되 **참조할 DSA 화면이 다르다** |
| 3 | **출결현황 미사용** | 그러나 `D.Lab` 메뉴는 사용이다. 출결을 그쪽에서 본다(DSA 실사의 "D.Lab > 출결 관리"와 일치) |
