# 입학 상담 신청 — 모델·화면 설계

> 근거: 2026-09-18 연구소 답변서. **확정된 것과 아직 아닌 것을 섞지 않는다** — 아래 2장은
> 지금 만들어도 되고, 3장은 시너지(홈페이지 개발사)와 전송 방식이 정해질 때까지 비워 둔다.

---

## 1. 왜 새 도메인인가

기존 `consult` 에 넣을 수 없다. **물리적으로 안 된다.**

```java
// ConsultLog
@JoinColumn(name = "enrollment_id", nullable = false)
private StudentEnrollment enrollment;
```

입학 상담은 **아직 학생이 아닌 사람**이고 등록 건이 없다. `nullable` 을 풀면 *"재원생 상담"*
이라는 그 테이블의 전제가 무너져 조회·통계가 전부 흔들린다.

⚠️ **`ConsultType.ADMISSION` 은 「입학」이 아니라 진학(대학) 상담이다.** 이름 때문에 여기로
넣기 쉬우니 주의한다.

그래서 `domain/admission` 을 새로 둔다. **입학확정 시점에 기존 신규 접수 경로로 넘긴다**
(`POST /admin/students` — 학번 서버 채번이 이미 있다).

---

## 2. 지금 확정된 것 — 저장 대상

전송 방식과 무관하게 *"무엇을 저장하는가"* 라 먼저 잡아도 안전하다.

### 2.1 신청 (`admission_inquiry`)

| 컬럼 | 비고 |
|---|---|
| `academy_id` · `year` | 지점·연도 (공통컬럼, §7) |
| `inquiry_type` | `CONSULT`(상담 예약) / `WAITING`(대기 예약) |
| `applicant_name` · `phone` | 신청자 |
| `student_name` · `grade_type` | 대상 학생 |
| `admission_type` | **모집 전형. `CONSULT` 일 때만 쓴다** — 대기 예약에서는 빠진다 |
| `preferred_at` | 희망 일시 |
| `status` | 아래 6종 |
| `editable_until` | 수정 가능 기한 (3장 참고) |

**★ 계열 항목은 넣지 않는다.** 수집도 노출도 하지 않기로 확정됐다 — 컬럼을 만들어 두면
화면이 언젠가 채우게 되고, 그때는 *"안 쓰기로 한 값"* 이 쌓인 뒤다.

### 2.2 동의 (`admission_inquiry_consent`)

**★ 세 종류를 각각 저장한다. 한 줄로 합치지 않는다.**

- 개인정보 수집·이용
- 마케팅 목적
- 광고성 정보 수신

DSA 도 3개 필드로 받고 있다. 합치면 **나중에 마케팅만 철회하는 것이 불가능해진다** —
약관 동의를 플래그가 아니라 이력으로 둔 것과 같은 판단이다(§2 약관 항목).

### 2.3 진행 상태 — 6종

```
통화필요 → 상담취소 · 상담완료 → 입학보류 · 입학확정 · 미등록
```

**★ 재적 상태(`EnrollmentStatus`)와 다른 축이다. 섞지 말 것.**
재적은 *"학생이 지금 어떤 상태인가"* 이고 이건 *"신청 건이 어디까지 처리됐나"* 다.

**두 축이 만나는 지점은 「입학확정」 하나뿐이다.** 거기서 학생을 만들고, 그 뒤로는
재적 상태가 이어받는다. 상태 변경은 이력으로 남긴다 — 누가 언제 어느 상태로 옮겼는지가
없으면 *"왜 미등록으로 바뀌었나"* 에 답할 수 없다(`enrollment_status_history` 와 같은 이유).

### 2.4 메모 (`admission_inquiry_memo`)

**열람 범위는 지점 메모 = 그 지점만, 본사 = 전체.**

★ **새로 만들 것이 없다.** `SearchScope.of(principal, year)` 를 그대로 쓴다.
⚠️ **`academyId` 를 요청 파라미터로 받지 말 것** — 값을 바꿔 보내면 다른 지점 메모가
새어나간다(§7).

## 3. 화면 — 조회 결과 버튼 3종

| 상태 | 버튼 |
|---|---|
| 수정 가능 기간 | 수정하기 |
| 수정 중 | 이어서 수정 |
| 기간 후 | 조회만 |

**★ 기준일 판단은 서버가 한다.** 화면이 판단하면 단말 시계가 다를 때 지점마다 결과가
갈리고, 기한이 지난 뒤에도 수정 버튼이 눌린다. 응답에 **상태값 자체를 실어 내린다** —
날짜만 내리고 화면이 비교하게 두지 않는다.

---

## 4. ★★ 수신 경로는 이미 있다 — 새로 규격을 정하는 일이 아니다

> **2026-09-18 정정.** 답변서 정리본의 *"신청 데이터가 우리 쪽으로 들어오는 경로가 아직
> 없습니다"* 는 사실과 다르다. 코드에 이미 있다.

```
POST /dlab/setStdInfo   입학예약 저장 (규격서 3.3) → rsv_cd 반환
POST /dlab/getStdInfo   조회 (3.4)
POST /dlab/getComInfo · /dlab/getSubInfo   공통·부가 정보
```

`domain/admission` 도 이미 있다 — `AdmissionReservation`(규격서 필드 그대로) ·
**`AdmissionFile`(첨부)** · `AdmissionScore` · `HomepageTokenService`(토큰 검증).

**즉 구조가 키오스크와 같다.** 우리가 DSA 자리에 앉아 **같은 규격으로 응답**하고 있고,
홈페이지는 아직 DSA 를 부르고 있을 뿐이다. → **시너지가 할 일은 새 규격 협의가 아니라
`base URL` 전환일 가능성이 높다.** 전송 방식·항목을 처음부터 정하는 협의로 잡으면
양쪽 모두 없던 일을 하게 된다.

### 그래서 시너지에 확인할 것이 바뀐다

1. **주소만 바꾸면 되는가** — 홈페이지가 부르는 DSA 주소가 설정 한 줄인지
2. **토큰·인증** — `HomepageTokenService` 가 검증하는 값을 그쪽이 그대로 쓸 수 있는지
3. **첨부** — `AdmissionFile` 이 있으나 **10MB × 4 가 규격서 범위인지 확인이 필요하다**
4. **실패 시 재시도와 멱등키** ⚠️ **답변서에 빠져 있다.** 같은 신청이 두 건 들어오면
   중복 제거를 사람이 하게 된다. `rsv_cd` 를 멱등키로 쓸 수 있는지 함께 본다
5. 오픈 시점

### 우리 쪽에 실제로 없는 것 (이건 만들어야 한다)

| 항목 | 현재 |
|---|---|
| **동의 3종** | `agree_ad` · `promo_ad` **2개뿐**이다. 개인정보 수집·이용 / 마케팅 / 광고성 수신 3종으로 나눠야 한다 |
| **상담 예약 / 대기 예약 구분** | 없다 |
| **진행 상태 6종** | 없다 |
| **관리자 목록·정식 접수 전환 API** | 없다 (QA 점검표 3.6 F05 미구현의 실체가 이것이다) |
| **계열(`geyul_gb`)** | ⚠️ **컬럼이 이미 있다.** 답변서는 *"전면 삭제"* 인데 규격서 필드라 수신 전문에는 남아 있다 — **저장·노출을 멈출지, 수신까지 뺄지 확인이 필요하다**
- **실패 시 재시도와 멱등키** ⚠️ **답변서에 멱등키가 빠져 있다.** 재시도하면 같은 신청이
  두 건 들어오고, **나중에 붙이기 어렵다** — 중복을 지우는 일은 사람이 하게 된다
- 오픈 시점
