# 프론트가 알아야 하는 서버 동작

**타입이 말해 주지 않는 것만** 적는다. 필드 목록은 `docs/openapi.yaml`(→ `schema.d.ts`)에
있고, 여기 있는 것은 **그 필드가 무슨 뜻인지**다.

> ★ **각 항목은 두 줄이다** — ①무슨 일이 일어나는가 ②**모르면 화면이 어떻게 깨지는가.**
> ②가 없으면 읽을 이유가 없어 안 읽힌다.

⚠️ **이 문서가 낡으면 화면이 거짓말을 한다.** 서버 동작을 바꾸면 **여기도 같이 고친다** —
PR 본문에만 적으면 프론트가 찾을 방법이 없다(2026-10-29에 그래서 화면 문구가 네 번 틀렸다).

---

## 1. 보호자 · 알림

### 1-1. 보호자는 **앱 계정이 없어도** 알림톡을 받는다

번호만 등록되어 있으면 수신자다. 수동 발송·미등원 배치·출결 알림이 **같은 판정**을 쓴다
(`GuardianRecipientResolver`).

⚠️ **모르면**: 「앱 가입 뒤에야 발송됩니다」를 적게 되고, 담당자가 **번호를 넣고도 기다린다.**

### 1-2. 보호자 번호는 **UNIQUE** 다 — 같은 번호면 **기존 보호자를 재사용**한다

새로 만들지 않고 **그 보호자에게 이 학생을 연결**한다. 형제자매가 보호자를 공유하므로
그래야 한다. **400이 아니다.**

★ 그리고 **입력한 이름은 버려진다** — 기존 행의 이름이 유지된다.

⚠️ **모르면**: 「같은 번호는 발송 때 한 명으로 합쳐집니다」처럼 **없는 동작을 적게 된다.**
그리고 번호 오타로 **남의 보호자에게 이 학생이 연결된 것**을 아무도 모른다 — 등록 결과에서
이름이 바뀐 것을 드러내야 한다.

### 1-3. 같은 학생에 같은 보호자를 두 번 연결하면 400

`"이미 연결된 보호자입니다."` — 다른 학생에 같은 보호자를 연결하는 것은 **허용**이다(형제).

### 1-4. 수동 발송: 대상이 0명이면 **400 + 사유**

```json
{ "error": { "code": "MANUAL_SEND_NO_TARGET",
  "message": "발송 대상이 없습니다. 연락처가 등록되어 있지 않습니다. (3명)",
  "data": { "blocked": [ … ], "summary": { "NO_PHONE": 3 } } } }
```

`blocked`는 **성공 응답의 `recipients`와 같은 모양**이다 — 파싱을 하나만 들면 된다.
`message`에는 **가장 많은 사유 하나**만 붙는다(전부 늘어놓으면 토스트에 안 들어간다).

★ **후보 자체가 0명이면 다른 문장**이다 — `"조건에 맞는 학생이 없습니다. 지점·학년·반
조건을 확인해 주세요."`

⚠️ **모르면**: 담당자가 **무엇을 고쳐야 하는지 모른다.** 연락처·앱가입·수신거부·허용목록이
전부 같은 문장으로 보인다.

### 1-5. 제외 사유 코드

| 코드 | 담당자가 할 일 |
|---|---|
| `NOT_ENROLLED` | — (재원 상태가 아니다) |
| `NO_GUARDIAN` | ★ **보호자를 등록**한다 |
| `NO_PHONE` | ★ 등록된 보호자에게 **번호를 채운다** |
| `NO_ACCOUNT` | 앱 가입 안내 — ★ **학생 수신 템플릿에서만** 온다 |
| `OPTED_OUT` | — (본인이 끈 것이다) |
| `OTHER_ACADEMY` | 선택에서 뺀다 |
| `NOT_IN_ALLOWLIST` | ★ 이관 기간 장치다(아래 1-7) |

⚠️ **`reason`을 닫힌 유니온으로 두지 말 것** — 늘어난다(2026-10-29에 `NO_GUARDIAN`이
늘었다). 모르는 코드는 **건수만** 보여주면 화면이 안 낡는다.

### 1-6. `blocked[].receiverName`이 `null`일 수 있다

**수신자가 정해진 뒤** 막힌 사유(`NO_PHONE`·`OPTED_OUT`·`NOT_IN_ALLOWLIST`)에만 실린다.
그 전에 막힌 사유(`OTHER_ACADEMY`·`NOT_ENROLLED`·`NO_GUARDIAN`)는 `null`이다 — **빠진
사람이 특정되지 않는다.**

⚠️ **모르면**: 「미지정」 같은 말을 넣게 되고, 담당자가 **그런 보호자가 있는 줄 안다.**

### 1-7. ★★ 수신 허용목록은 **비어 있으면 전면 개방**이다

`notification.allowlist`가 비면 전원 발송, 값이 있으면 **그 번호만** 통과한다.
이관 기간에 모르는 사람에게 가지 않게 하는 장치다.

★ **현재 상태는 운영 `.env`(`NOTIFICATION_ALLOWLIST`)에 있고 화면이 읽을 경로가 없다.**
2026-10-29 기준 **1개**가 들어 있다 — 즉 **지금은 전면개방의 반대**다.

⚠️ **모르면**: 반대로 읽어 「목록에 넣어야 간다」로 적게 된다. 그리고 **이관이 끝나고 비우지
않으면** 그 번호들만 알림을 받고 **화면에는 제외로만 남는다.**

### ★★ 그래서 화면은 「목록」이 아니라 **인원수**를 보게 한다

```
✗ 목록에 등록된 번호로만 실제 발송됩니다        ← ★ 목록이 비면 「없는 안전장치를 있다고」 말한다
✓ 허용목록이 적용될 수 있습니다. 미리보기에 나온 대상이 곧 발송 대상입니다
   — 보내기 전에 ★ 인원수를 확인해 주세요
```

★ **인원수는 서버가 판정한 결과 그 자체라 어긋날 수 없고, 목록이 비면 그 수가 커져서 눈에
띈다.** 화면이 허용목록 상태를 몰라도 담당자는 알 수 있다.

⚠️⚠️ **「없는 안전장치를 있다고 말하는 문구」가 가장 위험하다** — 숫자가 틀리는 것은 나중에
알아챌 수 있지만, **안 나갈 줄 알고 누른 것은 되돌릴 수 없다**(프론트 지적, 2026-10-29).

★ **상태를 응답에 싣지 않는 것도 의도다.** 내려주면 화면이 그걸 보고 **「목록이 비었으니
전원에게 간다」를 계산**하게 되고, 서버 판정과 **두 벌**이 된다 — 그 어긋남이 이 프로젝트에서
반복된 사고다.

### 1-8. 미리보기와 실제 발송은 **같은 판정**을 쓴다

`previewId`를 돌려보내므로 **미리보기에 나온 대상이 곧 발송 대상**이다. 조건이 바뀌면
미리보기를 버리고 다시 받는다. `previewId`는 **한 번만** 먹고 유효기간은 10분이다.

## 2. 권한 · 메뉴

### 2-1. ★★ 계정별 메뉴 지정은 **보이는 것을 줄이는** 기능이다 — 권한을 늘리지 못한다

역할에 없는 화면을 체크하면 **사이드바에는 보이고 들어가면 막힐 수 있다.**

⚠️ **모르면**: 「체크하면 열립니다」로 적게 되고, 담당자는 **설정이 틀린 줄 안다** — 빈 화면도
아니고 **오류 화면**이라 더 그렇다.

### 2-2. 미리보기로 **저장 전에** 결과를 본다

`POST /admin/staff/accounts/{id}/menus/preview` — 본문은 `PUT`과 같고 **저장하지 않는다.**

```
visible   편집본 기준 메뉴에 나오는가
level     FULL | PARTIAL
note      PARTIAL 이면 왜 그런지
```

★ **`PARTIAL`은 「안 열린다」가 아니라 「확인이 필요하다」다.** API 권한이 컨트롤러마다
흩어져 있어 **서버도 목록으로 들고 있지 않다** — 역할 기본 노출을 근거로 한 추정이다.

⚠️ **모르면**: 「열리지 않습니다」로 단정하게 되고, 실제로는 열리는 화면을 **막힌다고
안내한다.** `note`를 그대로 쓰는 것이 가장 안전하다.

### 2-3. `restricted`는 **필수**다

```
{"restricted": false, "menuCodes": []}        역할 기본값 사용(개별 설정 삭제)
{"restricted": true,  "menuCodes": ["student"]}  이 둘만
{"restricted": true,  "menuCodes": []}        400 (계정 정지로 처리할 것)
```

⚠️ **모르면**: 빈 목록 하나에 두 뜻이 겹쳐, 「전체 해제」를 누르고 저장하면 **정반대로 전부
열렸다**(실제로 그랬다).

### 2-4. ★★ 권한을 바꾸면 **그 계정이 즉시 로그아웃된다**

계정 중지·잠금·임시 비밀번호 재발급·**역할 변경**·**계정별 메뉴 변경** — 여섯 자리에서
기존 로그인이 **다음 요청에 끊긴다.** 다시 로그인하면 새 권한으로 들어온다.

★ **자기 계정을 바꾸면 본인도 로그아웃된다** — 정상 동작이다.

★ **「다음 로그인부터 반영됩니다」는 틀리다.** 바로 적용된다.

⚠️ **「1초 창」**: 설정과 **같은 초에 발급된 토큰은 살아남는다.** 임시 비밀번호를 재발급하고
바로 로그인하면 즉시 튕기던 것을 막는 폭이다 — **화면에 적을 값은 아니다**(담당자가
1초를 세게 된다).

⚠️ **모르면**: 「최대 1시간 더 쓸 수 있습니다」처럼 **옛 동작을 적게 된다.**

## 3. 목록 · 개인정보

### 3-1. `academyId`를 **마음대로 보내도 되는 것이 아니다**

받는 API가 있지만 **서버가 권한을 검사한다** — 자기 지점이 아니면
`OTHER_BRANCH_ACCESS_DENIED`다. 전 지점 권한자가 지점을 **안 고르면** 거절하는 API도 있다
(`"지점을 지정해야 합니다."`).

⚠️ **모르면**: 「지점을 안 보내면 전 지점」으로 가정하게 되고, **화면이 빈 것처럼 보인다.**

### 3-2. ★★ 마스킹된 값을 **그대로 재업로드하면 「변경 없음」**이다

`010-****-1234`를 보내면 **그 칸을 건너뛴다**(기존 등록은 DB 값 유지, 신규 등록은 400).

⚠️ **모르면**: 「내려받아 수정 후 재업로드」에서 **전 학생 연락처가 마스킹 문자열로
덮어써진다.** 그러면 미등원 알림톡이 가지 않는데 **화면에는 원래도 마스킹돼 보여 한동안
아무도 눈치채지 못한다.**

### 3-3. 응답의 `masked` 플래그를 쓴다

가려진 값인지 서버가 알려준다.

⚠️ **모르면**: 「번호가 잘못 저장됐다」는 오인 문의가 생긴다.

## 4. 수정 요청의 `null`과 `""`

### 4-1. 상벌점 항목의 분류·설명

```
null  ★ 기존 값을 그대로 둔다 (보내지 않은 것으로 본다)
""    ★ 지운다
```

옛 호출이 `null`을 넘기므로 그래야 **이름만 고쳐도 분류가 사라지지 않는다.**

⚠️ **모르면**: 「비우기」를 구현할 방법이 없다고 보거나, 반대로 **이름만 고쳤는데 분류가
사라진다.**

## 5. 결제 · 급식

### 5-1. 결제는 **수납·급식 공용 도메인**이다

급식 주문(`MealOrder`)에는 결제일자가 없지만, **결제 내역은 `payment`에 있다.**

```
GET /api/v1/app/payments              결제일자순 전부 (paidAt · 취소 표시 포함)
GET /api/v1/admin/billings/students/{enrollmentId}   그 학생의 청구 전체 (완납 건도)
```

⚠️ **모르면**: 급식 화면만 보고 **「결제일자가 없다」·「학생 단위 조회가 없다」**로 판단한다
(2026-10-29에 그랬다).

## 고칠 때

이 문서는 **서버 동작이 바뀌는 PR에 같이 넣는다.** ⚠️ 특히 **「없다」고 알려 준 것이 생기면
반드시 여기 적는다** — 프론트는 그 말을 **화면 문구로 박아 두고**, 나중에 사실이 바뀌어도
코드 주석만 고쳐지고 화면은 지나친다.
